MVP: Чат (Next.js + Postgres + Socket.IO)

## 🎯 Цель
Реализовать простой и надёжный чат 1-на-1 без SaaS (без Stream), с хранением данных в Postgres и realtime через Socket.IO.

---

# 📦 Общая архитектура

## Технологические ограничения и принятые решения
- авторизация уже реализована через **Better Auth**
- доступ к Postgres осуществляется через **Kysely**
- UI строится на базе **shadcn/ui**
- чат остаётся **1-на-1**, без групповых чатов
- цель MVP — максимально переиспользовать готовые open-source решения и не писать инфраструктуру с нуля

## Компоненты:
- **Next.js** — frontend + API + авторизация
- **Postgres** — хранение данных
- **Kysely** — типобезопасный SQL query builder (вместо ORM)
- **Socket.IO (отдельный сервер)** — realtime коммуникация

---

# 🧱 MVP функциональность

## 1. Пользователи
- авторизация уже реализована через **Better Auth** (интеграция с Next.js)
- используем существующую сессию/токен
- уникальный userId берётся из текущей системы

## 2. Чат (только 1-на-1)
- создание диалога между двумя пользователями
- список диалогов
- проверка: один диалог на пару пользователей

## 3. Сообщения
- отправка текста
- получение сообщений в realtime
- сохранение в Postgres
- сортировка по времени

## 4. История сообщений
- загрузка последних сообщений
- пагинация (infinite scroll)

## 5. Unread сообщения
- хранение последнего прочитанного сообщения
- подсчёт непрочитанных

## 6. Optimistic UI
- сообщение появляется сразу
- подтверждение с сервера

# 🧩 Рекомендуемые библиотеки и заготовки

## Обязательная база
- **Socket.IO** — realtime, комнаты, acknowledgements, reconnect
- **Kysely** — доступ к Postgres и типобезопасные запросы
- **Better Auth** — существующая авторизация, которую переиспользуем и для сокет-подключений
- **shadcn/ui** — базовые UI-компоненты приложения

## Что можно взять готовым

### 1. Realtime-ядро
- **Socket.IO Private Messaging Guide** — основная reference-реализация для 1-на-1 чата
- используем как основу для rooms, direct messages, reconnect и persistence flow

### 2. Фундамент приложения и БД
- **Next.js + Postgres + Kysely starter** — стартовая база для серверной части и работы с Postgres
- используем как инфраструктурный foundation, не как готовый чат

### 3. UI-компоненты
- **miskibin/chat-components** — выбранный UI-слой для чата
- используем как стартовую библиотеку/референс для chat UI поверх **shadcn/ui**

## Shortlist: что берём в MVP

### Берём
- **Better Auth** — текущая авторизация, без замены
- **Kysely** — текущий доступ к данным, без замены
- **Postgres** — основное хранилище сообщений и диалогов
- **Ably** — managed realtime-инфраструктура (вместо собственного Socket.IO сервера)
- **miskibin/chat-components** — UI-компоненты чата
- **shadcn/ui** — базовая дизайн-система приложения

### Не берём
- **Prisma / Drizzle** — не нужны, так как уже выбран Kysely
- **Stream / другие SaaS chat SDK** — не подходят, так как данные должны храниться у нас
- **ChatCN** — не выбран, так как избыточен для текущего MVP
- **Socket.IO (свой сервер)** — не используем из-за усложнения инфраструктуры и деплоя
- **групповые чаты** — исключены из scope
- **сложное масштабирование (Redis, multi-node)** — не входит в MVP
- **typing / presence / attachments / reactions / threads** — не входят в MVP

### Решение по realtime (Ably)

#### Почему выбран Ably
- полностью совместим с **Vercel** (не требует отдельного сервера)
- позволяет сохранить **простую архитектуру деплоя** (один Next.js проект)
- не требует настройки WebSocket-инфраструктуры, scaling и DevOps
- быстрее всего позволяет реализовать MVP (экономия времени разработки)
- дешевле и гибче по pricing, чем альтернативы типа Pusher при росте

#### Что мы получаем
- managed realtime (pub/sub, каналы, события)
- автоматическое масштабирование
- стабильные соединения и reconnect из коробки
- отсутствие необходимости поддерживать свой realtime backend

#### Что мы осознанно принимаем
- зависимость от внешнего провайдера (vendor lock-in)
- часть realtime-логики завязана на API Ably
- потенциальные расходы при росте (но приемлемые для MVP)

#### Архитектурный принцип
- Next.js (Vercel) остаётся единственным backend-приложением
- Ably используется как внешний realtime-слой
- Postgres остаётся источником истины для сообщений
- Ably используется только для доставки событий в realtime

### Принцип интеграции
- не пишем чат полностью с нуля
- собираем решение из готовых слоёв:
  - auth: Better Auth
  - db: Postgres + Kysely
  - realtime: Ably
  - ui: miskibin + shadcn/ui
- кастомная разработка остаётся только в бизнес-логике чата и интеграции между слоями
